# CSS declaration boundary and allocation batch

Requirement: default browser-facing CSS declarations must match jsdom's public WebIDL behavior while retaining fresh computed snapshots at lower allocation cost. The preceding query/style checkpoint is the frozen performance and qualification baseline. The boundary is the public declaration wrapper; the existing native-backed parser/cascade remains private.

Reference evidence from jsdom 30.1.3: own supported indices are readonly/enumerable/configurable; numeric writes and definitions reject even outside the supported range; noncanonical index strings remain ordinary expandos; preventExtensions returns false. Implementation maps are absent. CSSStyleDeclaration owns the seven declaration members plus parentRule/length/cssText, while CSSStyleProperties owns property accessors. Item performs unsigned-long conversion and required-argument checks. Computed results are fresh and retain earlier values. Existing owned tests permitting freezing and exposing a native constructor chain contradict this reference and must be corrected explicitly.

Public APIs remain element.style, rule.style, getComputedStyle and the two existing interface constructors/prototypes. No package export or capability option is added. Invalid receivers and required-argument/conversion failures throw TypeError; readonly mutation preserves NoModificationAllowedError. Foreign-window borrowed operations use the receiver's private implementation without leaking it through author-overridden public methods. Inline/rule wrappers remain SameObject; computed wrappers are fresh. Index reflection uses private declarations, and private completed storage never escapes through expandos or inherited helper methods.

Examples/tests: hidden storage and prototype surfaces on inline/rule/computed declarations; indexed writes/definitions/deletions and ordinary expandos; rejection of preventExtensions/freeze; required arguments and unsigned-long item conversion; foreign borrowed methods and invalid receivers; public overrides cannot receive private frames; retained snapshots after DOM/CSSOM mutations. Tests live in packages/jsdom/test/css-declaration-view.test.ts and the corrected computed-reuse tests. Existing full CSS/query/API/runner contracts remain active.

Stages: (1) reference-proven red public contracts and a private/public boundary for all declaration sources; (2) share immutable completed read contexts behind fresh public views, remove obsolete copy-on-write map code, retain owner/realm/readonly behavior; (3) full release and packed API/type/runner gates, frozen matched timing/CPU/allocation/memory including TurboDOM and Happy DOM, then exact-runtime full/local/legacy replay. Do not run measurements concurrently with correctness/build jobs. Preserve rejected experiments and source identities; reject speed claims from failed contracts. Update performance findings, qualification, DOM README and project guide only with observed results.

Implementation evidence: one private declaration record now owns every declaration-bearing CSS rule; attachment and cascade never invoke replaceable rule.style getters. A reference probe and owned red/green test establish this behavior. Fresh views reuse an implementation-owned index handler and publish one weak receiver record. A shared-property-descriptor experiment passed contracts but regressed warm role work about 6% without useful first-use gains, so it was removed; preserve css-view-metadata-prepared/comparison as negative evidence.

Memory/identity evidence: the compatible implementation uses about 64.11 MiB after work at 32 CSS-active windows, versus 51.78 MiB at the preceding checkpoint. The rejected shared-descriptor candidate reduces that to 56.60 MiB but shares public getter/setter function identity across Windows, contradicting jsdom. A direct reference/chosen/experiment probe and a public accessor-isolation regression pin that requirement. Keep the compatible per-window functions and report the retention tradeoff; future lazy property materialization must preserve reflection, mutation and function identity before claiming a memory win.

Next measured optimization boundary: public accessor functions must remain distinct per Window. A build-time-generated TypeScript class factory could share compiled method bodies and one Window context rather than allocating one lexical context per property; it must retain all descriptors/overrides/foreign receivers and measure the extra lazy module compilation cost before adoption. A prototype proxy would add substantial reflection/mutation complexity and is not justified while ordinary class generation remains unexplored. Also investigate whether the module-global private stylePropertyPrototype setter closures retain the first interface factory's realm/view context. This is an unproven retention hypothesis: require fresh-process WeakRef/GC evidence before hoisting that factory or claiming a leak. No such optimization is part of the frozen candidate.
