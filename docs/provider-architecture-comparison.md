# Happy DOM and TurboDOM architecture comparison

The comparison uses the packages installed in the frozen performance cohort, Happy DOM 21.0.4 and TurboDOM 0.7.1. RunDOM uses its default TypeScript parser. The full matrix ran on Node 24.20.0 and Apple M4. This follow-up adds 30 checked CPU profiles, 12 checked sampled-allocation profiles, and a three-provider probe of identity, mutation, reflection and teardown. Profile times attribute work within a run. The uninstrumented matrix supplies the performance comparisons. Allocation samples describe transient churn, while peak RSS includes JavaScript, native memory, buffers and allocator behavior. ## What makes Happy DOM faster in its winning cases

**CSS has a smaller cold path and a cheap reuse boundary.** `BrowserWindow.getComputedStyle` creates one declaration per element. A getter asks `CSSComputedStyle` for its property manager, which can return a weakly cached result before walking ancestors and matching sheets. Cache entries are registered against the document and relevant ancestors so invalidation clears their result. The behavior probe returned the same declaration twice and an old reference saw a subsequent inline edit. RunDOM returned fresh declarations and the earlier snapshot retained its value. Fresh RunDOM profiles attributed 27.25 ms of inclusive samples to vendor shorthand initialization across the first-read captures. Happy DOM goes straight through its own property manager, with less CSS value infrastructure. Its stylesheet invalidation and snapshot screens show gaps in the measured contracts. [Happy DOM public declaration](../.cache/performance-lab-GqdMhH/happy-dom/node_modules/happy-dom/lib/window/BrowserWindow.js#L1760) · [Computed-style cache and invalidation registration](../.cache/performance-lab-GqdMhH/happy-dom/node_modules/happy-dom/lib/css/declaration/computed-style/CSSComputedStyle.js#L221) · [RunDOM first-read profile](../.cache/performance-lab-GqdMhH/cpu-O5yC6k/analysis.md#run-dom-style-read--first-use)

**Selectors have a direct parse-and-match path.** Its selector parser caches parsed groups per Window and the matcher works on its own element arrays. `querySelectorAll` can return the same NodeList through a weak reference. RunDOM’s complex selector path normalizes syntax, adapts the css-tree AST, generates selector text for css-select, and compiles it. Both competitors’ lower cold query latency is consistent with removing that multipass boundary. For warm role queries the fresh profile also shows accessible-name and role matching in Testing Library. The full scenario spends time outside DOM style reads. Happy DOM’s successful complete bulk iteration is only slightly faster than RunDOM in this replay, and the public snapshot screen fails. [Happy DOM selector parser](../.cache/performance-lab-GqdMhH/happy-dom/node_modules/happy-dom/lib/query-selector/SelectorParser.js#L109) · [Result cache](../.cache/performance-lab-GqdMhH/happy-dom/node_modules/happy-dom/lib/query-selector/QuerySelector.js#L38) · [RunDOM adapter](../packages/dom/src/selectors.ts#L747)

**Its memory advantage is specific to lifecycle and workload.** The direct CSS path has lower peak RSS for the first style read, 134.0 versus 160.7 MiB. Closing 32 styled Windows drops Happy DOM’s heap from 153.5 to 34.2 MiB because the benchmark calls `happyDOM.close()`, which destroys the document, clears node arrays, attributes and caches, and releases Window services. The probe’s retained Window had empty body content after close. RunDOM preserved that content. Happy DOM’s live CSS heap was higher, and its dense replacement costs were much worse. The new large fragment allocation profile places Map and Node construction at the top of Happy DOM’s sampled frames. A smaller released heap of 25.5 MiB is a useful lifetime comparison, with the different teardown contracts limiting attribution. [Benchmark adapter](../packages/jsdom/bench/lab/providers.ts#L66) · [Happy DOM destruction](../.cache/performance-lab-GqdMhH/happy-dom/node_modules/happy-dom/lib/nodes/node/Node.js#L874) · [RunDOM close](../packages/dom/src/window.ts#L17433)

## What makes TurboDOM faster or smaller

**Document parsing, retained topology and wrappers are designed together.** It packs native parser output into typed views, unpacks once, and retains up to 64 entries by HTML source. Each document owns its wrapper cache and modified child or attribute storage. Most original data stays in shared columns. `__nodeAt` constructs a handle once per index when requested. RunDOM already skips parsing recurring input, but then copies a fresh mutable object graph from its private recipe. The new dense allocation captures attribute 36.3 MiB of warmup samples to this copy and 14.1 MiB to RunDOM’s Node constructor. TurboDOM’s full traversal still allocates child arrays and wrappers. The warm gap shrinks from 15.75 ms for recurring full traversal to 6.93 ms on the distinct, unique-parsing scenario. The unique-input row has a different workload, so it bounds the interpretation of the cache advantage without isolating native tokenizer speed. [TurboDOM cache and factory](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/index.mjs#L30) · [TurboDOM wrapper inflation](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/dom.mjs#L2240) · [RunDOM copy](../packages/dom/src/private-template-copy.ts#L69)

**Fragment replacement uses a separate, narrower path.** TurboDOM calls native `parseFragment` for a nested result, eagerly inflates the owned subtree, sets parents, publishes one child array and emits a child-list record only when observed. Its peak-RSS lead on fragment-list readback is real in this workload. Its warm batch and total process time both trail RunDOM, 64.70 versus 32.43 ms and 576 versus 393 ms. RunDOM’s new CPU profile exposed two comparable warmup costs in its checked replacement path, about 13.4 ms inclusive under parse5 tokenization and 15.2 ms under replacement. At 4,096 rows the allocation profile shows large samples in descendant iteration, document name and ID bookkeeping, shadow-including scans and details reconciliation. The profile narrows the opportunity to avoiding repeated insertion work and transient allocations. Replacing the parser alone leaves that work intact. [TurboDOM fragment parsing and installation](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/dom.mjs#L1278) · [RunDOM fragment replacement](../packages/dom/src/window.ts#L3450)

**Window and CSS costs scale with features actually touched.** TurboDOM’s module-level global table provides shared constructors and methods. A proxy handles Window overrides and materializes most per-Window capabilities on access. The probe observed 10 initial own keys and shared Node constructors, compared with RunDOM’s 490 and separate constructors. Its Window `close` binding is a no-op in this version. The benchmark constructs new environments and never calls the separate arena-reset API. TurboDOM also caches computed-style proxies by document version and returns cached query results directly. The probe found that an old style result retained its value after mutation, but two reads before mutation returned the same object. It also returns the same array for repeated bulk queries and lacks `item()` on that result. The full matrix preserves those contract failures. [TurboDOM lazy globals](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/window.mjs#L166) · [Close binding](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/window.mjs#L462) · [Versioned cascade](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/cascade.mjs#L212) · [Query result cache](../.cache/performance-lab-GqdMhH/turbo-dom/node_modules/@miaskiewicz/turbo-dom/src/runtime/dom.mjs#L22)

## Ranked RunDOM opportunities

### 1. Discover fragment effects during parsing and commit them once

Have the existing owned parse adapter retain a bounded set of relevant raw-node candidates while creating elements. Resolve candidate membership and final order against the completed parser tree because foster parenting and formatting reconstruction can reorder or discard candidates. At replacement, use the final tree and the old subtree’s known capabilities to prove which work is needed. Batch names and IDs, radio and details work, style and resource activation, Range updates and the one delivered mutation record in their existing order. A conservative fallback handles unproven scopes, existing shadow roots, parser extensions and reentrant cleanup. Start with the allocation-heavy list and table cases. Measure peak and released RSS alongside context-specific parse, install and readback separately. Require a clear peak reduction and preserved end-to-end throughput with and without observers, and check table foster parenting, custom reactions, inline script reentry, templates, range offsets and old-node identity. This differs from the rejected experiment that only swapped descendant iterators. [Parser-owned fragment transfer](../packages/dom/src/html-fragment.ts#L13) · [Post-insertion ordering](../packages/dom/src/window.ts#L19705) · [Prior fragment scan experiment](cold-css-dense-startup-performance.md#other-timing-and-memory-gaps)

### 2. Keep parser output packed as the canonical representation

Start with eligible inert parsed subtrees. Store immutable base topology and strings in a bounded arena, with independent per-document edits at a node, attribute span or edge. Give packed and subsequent JS-created nodes the same private traversal and mutation API. Walk packed nodes, read text and attributes, and compute selector candidates from IDs. Allocate each Window-local branded wrapper only when an API returns it. First build a measured slice for repeated and unique parse through full traversal and one edit. The old prototype relied on proxy-backed raw arrays and whole-tree promotion, so sparse gains came with dense costs. A valid replacement must avoid global promotion, improve dense and sparse work, preserve unique-input throughput and released heap, and honor adoption, detached nodes, Range, templates, snapshots, and brands. Reuse the existing native compact transport and validate ownership before considering a parser switch. [Prior promotion results](lazy-template-materialization-plan.md) · [Existing checked compact arena](../packages/html-parser/src/compact-arena.ts#L211)

### 3. Compile CSS rules into a reusable program and shrink the cold evaluator

Use the pinned grammar to validate immutable declaration instructions at sheet insertion or first rule use. Bind rule selection separately from declaration execution. Keep syntax and instructions transferable across Windows, and keep the CSSOM state and mutation generation receiver-owned. Then resolve supported simple computed values without installing the full private declaration descriptor machinery. Build a fresh indexed view from the frozen frame and use the existing complete evaluator for unsupported properties and dependencies. For Ant Design, measure insertion, first authored style, repeated invalidation and identical passing tests end to end. RunDOM already reuses completed frames on eligible reads, so caching them again leaves the expensive misses intact. Gates cover CSSOM edits, inherited and custom properties, layer and scope priority, logical shorthand order, URLs, fonts and frozen old snapshots. Prior efforts deferring vendor shorthand setup moved cost into descriptors and grammar. This cut needs to remove descriptor initialization from the common path altogether. [Current frame reuse](../packages/dom/src/styles.ts#L5629) · [Prior Ant Design and cold CSS results](antd-cascade-followup.md)

### 4. Split Window assembly by capability while preserving the public shape

Generate reusable private metadata and move state-free implementations out of the per-Window build. Instantiate Window-local public classes and prototype members before they become observable through construction or reflection. Keep own descriptor order and flags, cross-Window identity, borrowed receivers, VM behavior and patchability as contracts. Begin with a single independently reachable interface family and measure creation, first access, reflection replay, the full lifetime, and framework boot. The design pays for complete capabilities at the point they become observable, and avoids sharing mutable public prototype state. TurboDOM’s proxy and close shortcut cannot establish the attainable gain for the full contract. [RunDOM Window assembly](../packages/dom/src/window.ts#L2030) · [Prototype and global reflection results](antd-cascade-followup.md#remaining-gaps-and-controls)

### 5. Compile selectors directly from one validated representation

Unify production of the grammar’s internal representation, matcher code and candidate-index hints. Eliminate the serialize-and-parse-again boundary while keeping strict CSS feature queries, forgiving branches, Unicode/escape handling, namespaces, current control state and stylesheet specificity. Preserve the existing fast paths for simple selectors, and use fresh public lists with shareable private membership. Start with cold diverse selectors in the default matrix, then measure mutation-heavy selectors and parsed stylesheet creation. The first query gap is about 15 ms against both providers. Much of the warm role path sits in Testing Library and accessible-name computation, so the role row alone is a poor gate for this project. [Current selector compiler](../packages/dom/src/selectors.ts#L747) · [Candidate indexing](../packages/dom/src/query-index.ts#L16)

### 6. Give derived state an explicit Window lifetime

Inventory which objects a previously returned Node, Range, style snapshot or collection still needs after `close()`. Give reconstructible style, selector and layout caches an owning container with a clear-and-rebuild boundary, so closed Windows release those caches while private authoritative tree state remains usable. Measure live, closed-with-handles and released heap separately. Exercise retained same-object views, detached handles, in-flight cancellation and reads after close. Happy DOM identifies how much teardown can reclaim, while the post-close probe establishes the cost of retaining RunDOM’s behavior. Treat this as a memory project with retained-heap gates, independent of peak fragment RSS. [Current close path](../packages/dom/src/window.ts#L17433) · [Close behavior probe](../.cache/provider-architecture-followup/contracts.jsonl)

Start with fragment-effect discovery. The allocation profile points to a concrete removable cost inside the existing parser boundary, and RunDOM already has a throughput lead to protect. Build the packed representation as the larger independent project. That is the change with the broadest reach across repeated creation, traversal, mutation and live heap. Evaluate the CSS program against Ant Design’s complete passing selection before investing in a larger Window or selector refactor.
