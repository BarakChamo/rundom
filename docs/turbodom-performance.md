# TurboDOM performance investigation

Inspected version: **0.7.1**, the pinned competitor in the November 7 matched performance cohorts. The source of record is the installed package in `.cache/performance-lab-NH7dwk/turbo-dom/node_modules/@miaskiewicz/turbo-dom`; its lock and runtime hashes are recorded in that cohort's manifest. The older `.cache/qualification/turbodom-consumer` contains 0.6.0 and is not the source for this investigation. These findings come from implementation inspection and checked workloads, not the package's performance claims.

## Mechanisms and boundaries

| Mechanism                                                                                  | Source in the installed package                                    | Consequence and adoption boundary                                                                                                                                                                                                                                                           |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Native Rust parsing with WASM fallback, resolved once on first parse                       | `src/runtime/parser.mjs`, `src/core.rs`, `src/lib.rs`              | Native execution is only one part of construction. Measure parsing, transport, decoding and wrapper creation separately before selecting a backend. RunDOM's existing Rust end-to-end result remains slower than its TypeScript path.                                                       |
| Packed structure-of-arrays buffer, typed-array views, interned string tables               | `src/runtime/buffer.mjs`, `unpack()`                               | Tree topology is read without first allocating every DOM node or attribute object. `attrGet`/`attrHas` scan packed columns directly. This is an architectural candidate for RunDOM's native boundary, requiring ownership, namespace, adoption and mutation tests.                          |
| Lazy identity-memoized node handles and copy-on-write overlays                             | `src/runtime/dom.mjs`, `Document.__nodeAt`, `__load`, `__children` | A fresh document shares immutable parse data while materializing only touched nodes. The per-document handle cache preserves identity; writes create owned state. Benchmark sparse and full-tree access, mutations and retained windows rather than construction alone.                     |
| Process-wide 64-entry HTML parse LRU, including unpacked views, with last-key shortcut     | `src/runtime/index.mjs`, `parseBufferCached()`                     | Identical HTML can skip Rust parsing, boundary transfer and unpacking entirely after its first use. Entry count is bounded, but retained source/buffer bytes also need a budget. Repeated-shell and unique-HTML tests must be separate; the warm parse result is not raw parser throughput. |
| Shared environment-independent global factories and lazy per-window globals                | `src/runtime/window.mjs`, `createWindow()`                         | Avoids constructing unused capabilities for each window. Preserve per-realm constructors, prototype isolation and descriptors when exploring this in RunDOM. Shared factories are safer than blindly sharing public mutable constructors.                                                   |
| Per-node selector-result maps keyed by document version; globally unique mutation versions | `src/runtime/dom.mjs`, `cachedQS`, `cachedQSA`, `__touch`          | Repeated unchanged queries become map lookups. The version counter avoids accidental hits after adoption. RunDOM already caches bounded weak result vectors; any further change must preserve validation, live selector state and fresh public views.                                       |
| Cached selector parsing and low-allocation matching                                        | `src/runtime/selectors.mjs`                                        | Useful independent of result reuse. Compare varied selector strings, misses and mutation-heavy cases to expose parsing versus traversal costs.                                                                                                                                              |
| Computed-style result reused per element/document version                                  | `src/runtime/cascade.mjs`, `makeGetComputedStyle()`                | Avoids both cascade and view allocation on hits. Its explicit curated inheritance set and cached public identity differ from the complete jsdom contract. RunDOM may reuse private completed frames, while retaining required fresh public identity and previous snapshot values.           |
| Reset an existing environment onto another buffer                                          | `src/runtime/index.mjs`, returned `reset()`                        | Can amortize environment setup, but is a separate API/workload from constructing and closing independent JSDOM windows. The default comparative provider calls `createEnvironment`, not `reset`.                                                                                            |

Returning the exact cached `querySelectorAll` result is observable: `cachedQSA()` returns `c.r`, and the selector engine returns an array. The stricter checked workload requires a fresh NodeList with `item()`, independent expandos and retained members after mutation. TurboDOM fails the current snapshot and `item()` screens. This explains part of the repeated-read gap; it does not erase the useful packed/lazy/cache architecture or excuse RunDOM's remaining costs. Computed-style fresh-identity/snapshot, CSSOM rule invalidation and inherited-style screens also fail for TurboDOM in this cohort. Keep the raw failures rather than assigning a hypothetical speed for equivalent behavior.

## Experiments to prioritize

1. Attribute first-use and real Vitest interaction cost before replacing another subsystem. Warm roles still spend substantial time in computed frames and fresh view creation; a small cached-query win cannot explain the remaining framework gap.
2. Separate private CSS implementation from public WebIDL views, guided by reference probes for indices, hidden implementation fields, branding and extensibility. Explore cheaper fresh views over immutable completed data without returning the same public object.
3. Evaluate immutable parse snapshots and lazy materialization as one complete architecture experiment. Cover repeated/unique HTML, sparse/full traversal, mutations, parser modes and 1/8/32-window byte retention. Include transfer and first-touch costs, cross-document adoption and per-window identity. Only adopt with end-to-end gains and unchanged compatibility.
4. Test byte-bounded parse reuse and lazy capability initialization independently. Keep reduced capability settings and environment reset separately labeled; default drop-in semantics remain the target.

These are evidence-driven experiment candidates, not implemented changes or claimed wins. CPU/allocation profiles and timing must run after the active correctness replay, never concurrently with it.

## Attribution after the completed correctness replay

Separate TurboDOM role-query CPU and sampled-allocation trials use the same 256-row, five-batch, 8,192-operation diagnostic dimensions as the RunDOM passes. The CPU pass records 164.01 ms of instrumented warm work; leading non-instrumentation self times are `matchCompound` 32.58 ms, Testing Library `getImplicitAriaRoles` 21.25, `matchChain` 12.67 and `queryAllByRole` 10.96. Its cached `gcs` contributes 3.34 ms. This supports investigating RunDOM's computed-frame/view costs before expecting selector-only work to close the role gap. It does not measure equivalent complete CSS semantics, and instrumented durations are not speed ratios.

The separate allocation sample attributes 215.18 MiB to `getImplicitAriaRoles`, 57.28 to `queryAllByRole`, 28.94 to `matchCompound`, 24.65 to one `computeTextAlternative` frame and 20.74 to a `get` frame. These are sampled allocation churn, including collected objects, not retained bytes. Raw reports are indexed by `.cache/qualification/query-style-turbodom-role-{cpu,allocation}.json`; matching RunDOM reports use the `query-style-after-role-query` prefix. The profiler's instrumentation frames remain recorded but are excluded from workload self-time interpretation.

CSS-active lifetime trials add three verified fresh processes at each of one, eight and 32 windows for TurboDOM. ## Follow-up: actual adapter and native ownership experiments

The pinned 0.7.1 package publishes `environment/vitest` as an import-only export. Resolve it inside the independently installed framework consumer and run the same unchanged eight React/Testing Library workflows through that adapter. The new `benchmark:framework --include-turbo` path does this under the producer-resolution guard. In Vitest 5.1.0, forks and threads pass seven workflows but fail controlled checkbox activation; vmForks/vmThreads fail before tests because setupVM is absent. The adapter documents Vitest 1–4. Keep these integration failures and null timing rows; do not infer a complete framework speed from partial checks. Raw outputs are `.cache/framework-benchmark-PJvfO5`; diagnostic VM errors are `next-turbo-{vmForks,vmThreads}-diagnostic.log`.

Versioned private completed frames are useful independently of TurboDOM's cached public identity: RunDOM's final styled read is 2.308 ms versus TurboDOM 2.438 for the same value-checked 8,192-operation batch, while RunDOM retains fresh readonly snapshots. Happy DOM is 0.766. All are shared-host observations, and the stricter mutation/snapshot screens retain the providers' failures. RunDOM still trails TurboDOM on roles and construction.

The multi-entry parse-cache experiment follows TurboDOM's recurring-shell mechanism but remains rejected: modest rotating-shell gains accompanied unique-worker throughput loss. The existing one-entry template budget stays in production. Corrected unique-worker inputs reveal how strongly cache warmth changes the comparison: TurboDOM's final single/four-worker throughput is about 2,263/5,263 unique documents per second, versus RunDOM TypeScript 699/1,551. The former task-local sixteen-input repetition is invalid unique-throughput evidence.

Rust tendrils/atoms remove intermediate owned-string copies without changing the transport. Large unique end-to-end work improves roughly 11%, but TypeScript still wins that large-input row. The native system sample exposes tokenizer/character-buffer work and string-pool hashing, while Inspector also attributes substantial JS decode/materialization and wrapper cost. TurboDOM's shared packed parse data, lazy node identities, copy-on-write overlays and cheap global factories remain the larger architectural differences. A packed/lazy handoff experiment must include first touch, complete traversal, mutation, adoption, realm identity and retained-byte limits before selecting a new default backend. See [the current findings](optimization-opportunities.md#static-author-frames-and-native-ownership-qualified-follow-up) for exact data and source identities.

The event follow-up inspects the same installed 0.7.1 source (`src/runtime/events.mjs:9`). Its Event constructor writes public mutable fields, sets timeStamp to zero, and assigns isTrusted as an ordinary field. RunDOM retains timestamp calculation and an own nonconfigurable trust getter. Those costs cannot be removed while preserving the current event contract. A construction-specific scenario therefore checks the trust descriptor before admission; simpler existing dispatch scenarios establish only their checked dispatch behavior. The selected RunDOM experiment consolidates private weak metadata without changing public descriptors. Repeated native-input reuse is motivated by the same installed package's 64-entry parse cache (`src/runtime/index.mjs:35`), but RunDOM's proposed experiment stays at one entry with markup/node budgets and explicit actual native-call counts.

## Qualified mechanism follow-up — 2026-11-08

The deMMKD batch adopts recurring immutable-data reuse while preserving full per-window object ownership. Native caching stays at the checked-arena boundary; TypeScript caching keeps private unexposed templates. Eight-entry linear LRU admission with a most-recent shortcut avoids hashing full unique sources. Aggregate limits now accommodate large recurring shells, addressing the earlier experiment's capacity mismatch. Each native source requires two actual kernel parses before admission; public parseHTML/parseHTMLArena stay uncached. The matched rotating-input reductions are recorded in [performance findings](performance-lab-results.md), separate from fresh unique parsing throughput.

The inverse node-handle cache now uses an opaque field on private raw nodes, approaching TurboDOM's direct identity memoization without exposing packed indices or changing public wrappers. Shared ordinary-tree text aggregation removes leaf-chain scratch allocations while retaining XML/template rules. Per-window public constructors/prototypes, fresh NodeLists and computed snapshots remain unchanged. A complete initial Window shape experiment was slower and removed; TurboDOM's shared public-class setup remains an architectural advantage that cannot be copied directly under the current contracts. Full replay and remaining deficits are sealed in the material-gap checkpoint.
