# Upstream framework performance campaign

RunDOM should complete equivalent DOM workloads faster than jsdom, Happy DOM and TurboDOM. The benchmark gate checks the same test identities, statuses and counts in fresh serial processes. A provider's compatibility failures stay in the compatibility table. A named common selection can measure equivalent work while the full selection differs.

## Batch sequence

1. Screen the untouched upstream selection and record the actual provider, package version and revision. Keep setup, transforms, summed test duration, end-to-end elapsed and peak RSS in the raw report. Disable Vitest's filesystem transform cache as well as its result cache on versions that support both.
2. Use a worker CPU profile and allocation samples to identify the largest cost that RunDOM can control. Trace it to its source and estimate the maximum effect on the full workload before changing production code.
3. Compare candidates in a frozen package. Check fresh and repeated work, ensure equivalence of public behavior, and keep resource usage visible. Run the full repository gate and replay the upstream screen. Use alternating provider order and review the process-time ranges alongside the medians.
4. Return to the remaining measured costs. Keep synthetic or focused work tied to a real workload and record effects on the full suite separately.

## First bottleneck

Material UI reads styles shortly after Emotion inserts or changes stylesheet text. The cold read can discover the stylesheet, parse its selector syntax, validate declaration values, allocate rule/declaration objects and then perform the cascade. The initial profile attributed about 1.17 s to stylesheet construction under computed-style reads and another 435 ms to rule traversal. Ant Design pays most stylesheet construction during rendering, then spends about 500 ms in the computed-style path. These paths are documented with the exact profile frames and trial reports in [framework results](framework-compatibility-results.md#three-provider-follow-up).

Three approaches address stylesheet construction at its owner boundary. A per-Window selector cache avoids compiling stateful selector syntax repeatedly. Immutable declaration snapshots avoid revalidation of repeated flat blocks and restore separate mutable CSSOM state. Deferred materialization avoids validating declarations from flat rules whose styles nobody matches or inspects. The same public CSSOM objects, source ordering and live state remain observable. Existing style tests cover invalid syntax, rule ownership, mutation, nesting and snapshots. The added cross-window test covers edits to two copies of the same authored declaration block.

The allocation profile puts first CSS runtime initialization ahead of retained rule data for both React component suites. Of the sampled bytes under declaration interface initialization, Ant Design attributes about 36 MiB to Node VM script compilation and 18 MiB to CSS grammar descriptors. Material UI attributes 23 and 11 MiB to the same paths. The public declaration view constructor itself accounts for about 3 and 2 MiB.

## Startup and memory experiments

- A separate selector engine bundle reduced first `cssSelect` access from 8.16 to 2.97 ms and RSS from 62.7 to 48.2 MiB in nine paired fresh processes. RunDOM's general selector path also needs CSS-tree. With both capabilities active, the split took 12.00 ms and 67.7 MiB, versus 11.83 ms and 67.7 MiB for the shared bundle. With CSS validation and color capabilities loaded too, the split was also flat. The split was rejected. [Partition trials](../.cache/framework-css-partition/results.json)
- A prototype lazily built the original and patched CSS-tree grammars and kept the same parser. Parser and selector access improved from 11.96 to 8.32 ms and from 68.1 to 62.3 MiB. The first validated CSS property took 27.15 ms and 94.0 MiB, versus 24.65 ms and 91.7 MiB on the existing build. When both grammars were used, the regression grew to about 4 ms and 5.4 MiB. The prototype was rejected. [Grammar trials](../.cache/framework-css-grammar/results.json)
- Vitest's global setup read the public `window.WebSocket` constructor and loaded Undici during environment initialization. Profiles attributed 198 ms in Ant Design and 118 ms in Material UI to that getter under `populateGlobal`. Transport initialization now happens when a socket is constructed. The Window's public constructor and constants are still available immediately. The DOM regression checks transport initialization timing and the facade tests exercise real messages, close events and realm-local errors. [Before profiles](../.cache/framework-target-prefilter)

Material UI's follow-up profile attributes 418 ms of cascade work to focusability checks. Each eligible focus attempt walks ancestors and requests a complete computed-style view for each element to read `display`. Role queries account for a separate 544 ms of cascade work. In Ant Design the same focus path accounts for only 1 ms, while role queries account for 423 ms. A focus-only improvement can address part of Material UI's gap. A projection for general computed styles must also account for the visibility and content-visibility reads from accessibility queries. [Profile attribution](../.cache/framework-target-focus/profile-attribution.json)

In a diagnostic build, removing the focus display check entirely took Material UI from 8.684 to 8.451 s and from 408 to 360 MiB across three alternating pairs. Ant Design stayed near 6.0 s and its test-body median stayed near 1.75 s. The diagnostic passed the selected tests, but bypasses hidden-element behavior and is only an estimate of removable work. Its maximum elapsed saving falls short of Material UI's measured gap to Happy DOM. [Focus ceiling trials](../.cache/framework-target-focus/ceiling-results.json)

Reading `window.WebSocket` in seven paired fresh processes improved from 22.22 to 0.05 ms and from 80.7 to 70.3 MiB RSS at that point. A module-cache check confirms Undici first loads on socket construction, and an invalid socket URL still raises the Window's DOMException. The follow-up worker profiles sampled no time in the getter under Vitest global setup. Full-process RSS differs by workload and retains the values in the framework results table. [Getter trials](../.cache/framework-target-websocket/getter-probe.json), [Worker profiles](../.cache/framework-target-websocket/profile-after.json)

### Limits of caching repeated computed styles

TurboDOM caches the returned style by element and document revision. Instrumenting the full Ant Design workload found 369 computed-style reads. Of those, 139 were repeated reads of an element at the same style revision. RunDOM's existing complete-cascade reuse recorded zero hits. CSSOM exposure disqualified 157 reads. Pseudo-element and live-state selector rules blocked most of the remaining styled reads.

A diagnostic build returned the same computed style for every repeated element and revision. This bypassed the fresh public snapshot requirement and the state checks, so it served only to estimate the maximum saving from that strategy. It passed the selected 133 tests. Across three alternating pairs, the wall-time median moved from 5.934 to 5.873 s, and summed test time moved from 1,741 to 1,651 ms. This is substantially smaller than the measured Ant Design test-body gap. The remaining cascade cost includes the first read. [Diagnostic trials](../.cache/turbo-startup/cascade-ceiling.json), [Read counts](../.cache/turbo-startup/proof-reuse-events.log)
