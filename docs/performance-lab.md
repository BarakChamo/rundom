# Performance laboratory

The synchronous scenario helper carries one cumulative operation ordinal through first-use, warmup and measured batches. A batch of one operation must still change mutation values, rotate selectors and visit successive windows; resetting the ordinal at each batch can silently turn writes into unchanged assignments. The owned laboratory contract checks three successive single-operation attribute writes. Before/after cohorts must use the same helper revision. Reports made before this correction retain their original scope and cannot be directly mixed with corrected reports.

Use `bun run benchmark:lab prepare` once to build and freeze the current candidate. Save the printed absolute `directory` as the cohort path. Preparation installs pinned independent consumers for RunDOM (TypeScript and explicitly selected Rust), jsdom 30.1.3, Happy DOM 21.0.4 and TurboDOM 0.8.6. All measurement commands execute the cohort’s frozen driver and workers; analysis can be regenerated independently. It snapshots the TypeScript rig and records source, tarball, lockfile, installed-content, Node and platform identity. Measurement rejects changed installed content and producer dependency resolution. The default `--conditions shared-host` labels exploratory results; use `--conditions isolated-host` only after establishing exclusive use of the machine. Analysis refuses speed-comparison eligibility on a shared host. Timing runs must have exclusive use of the machine: stop builds, conformance, profiles and other benchmarks first.

CLI dimensions are bounded: tree size 1–8192, depth 1–64, live windows 1–64, operations 1–100000, batches 1–101, rounds 1–51. `--providers` and `--scenarios` are comma-separated selections. `--script-mode default|outside-only|dangerously` exercises explicit jsdom realm modes; providers without an equivalent contract fail the screen. Default tree size/depth/windows are 256/4/8. Default operations per batch are eight for creation/parsing/cloning/serialization (`windows-create-close`, `globals-read`, every `parse-html*` variant, `clone-subtree`, `serialize`) and 512 otherwise, with nine measured batches. Before 2026-11-27 only plain `parse-html` received eight; default-dimension reports of the other parse variants used 512 and are not comparable with newer ones. Parallel defaults use one scenario, parse-html, and eight operations per task. Lifecycle cleanup uses the provider’s documented management API: jsdom/RunDOM window.close(), and Happy DOM happyDOM.close(), awaiting disposal without replacing public methods. A real timer-cancellation contract checks this adapter. The default `--turn-policy between-batches` yields an event-loop turn outside timed work before each warmup/measured batch. `--turn-policy burst` retains synchronous burst scheduling explicitly; the policies cannot share a speed ratio. Neither forces GC in timing mode. A warmup is one first operation followed by eight batches of up to 32 operations. Set `--warmup-batches` (0–101) and `--warmup-operations` (1–100000) to study the JIT warmup ramp; the default is initial reuse, not proof of fully optimized V8 code. Every new worker verifies the exact requested cumulative operation count, and the driver independently checks it. Neither enters warmed-batch distributions. `--timeout-ms` bounds each child, default 120000.

## Checked scenarios

`control` exposes harness/loop cost without subtracting it. `windows-create-close` separates first and repeated allocation/lifecycle. `globals-read` constructs a Window and reads every own property once without guards, as Vitest's global population does for each test file; it checks a stable per-provider property count, `document` identity and core constructors. Its first-use phase carries the lazy-global activation cost that warm batches hide. `parse-html`, `fragment-write`, `clone-subtree` and `serialize` cover document/fragment and transfer-shaped work. `read-tree` reads topology, text and live child views. Query scenarios cover ID hits/misses, first selector use, compound matching, length-only results, full iteration, fresh static-snapshot identity, retained contents after mutation, class invalidation, diverse hit/miss selectors and batched writes. `style-snapshot` checks fresh jsdom-style identity and retained values across inline mutations. `windows-style-live` exercises CSS activation and computed reads across the configured live windows. Writes cover attributes, text and topology. Events cover synchronous bubbling and checkbox default action; MutationObserver measures writes through actual asynchronous delivery. Styles cover repeated computed reads, inline changes, CSSOM rule changes and inherited custom-property invalidation. Testing Library `role-query` checks target identity. `windows-live` measures independent documents with retained windows and per-document state.

Each operation checks its result or delivery count; no-op writes fail. Capability screens use the exact worker and checks, then fresh processes measure successful combinations. Failed screens/trials remain in JSON and stderr; incomplete combinations cannot support a performance comparison. Avoid an overall score that rewards missing APIs. Different operation counts, sizes, script modes, capability profiles or source builds must never be combined into a speed ratio.

## Evidence and attribution

Every serial worker reports provider load, setup, first-use, warmup, each warm batch and close wall/CPU times. Setup includes markup parsing and any Testing Library import. First-use may include deferred CSS initialization. Complete-worker process time includes Node, TypeScript harness loading, validation, snapshots and reporting; it is time to verified worker exit, not bare package import latency. Provider-load and first/setup phases expose the package portion. Cold means fresh module/process caches, with filesystem caches primed equally; it does not mean a reboot or cold disk. The package is not monkey-patched or timed with production tracing enabled.

Timing mode uses no Inspector, GC observer or forced GC. Reports retain every trial and every batch, median, median absolute deviation, minimum, maximum and empirical p95. Batches within a process are correlated; these p95 values describe batches, not individual operation tails. Nine process trials are a useful baseline, not a precise extreme-tail estimate. Sub-millisecond batches remain visible but are ineligible for speed certification; increase operation count and warmup before optimizing their ratios. Memory snapshots happen outside timed operations. CPU usage includes GC and native work; wall time includes waits. Do not subtract unrelated timings to invent stage costs.

Diagnostic CPU mode uses [Node Inspector](https://nodejs.org/docs/latest-v24.x/api/inspector.html) at a requested 100 µs sampling interval. Each phase retains a DevTools `.cpuprofile` plus `attribution.json` with self and inclusive time. DOM CJS source maps map frames back to TypeScript; dependencies without maps retain actual function/file locations. Inspector start/stop can dominate tiny profiles; derived reports label instrumentation self time, retain it in JSON and show workload frames in readable rankings. Profile duration and the timed operation duration are separate. Inclusive costs overlap and must not be summed. Tiny phases have few samples; increase operation count before drawing conclusions. Sampling shows JavaScript/native-boundary cost, not Rust internal symbols; use a native profiler before deciding which Rust function to rewrite.

Allocation mode retains `.heapprofile` samples at a requested 16 KiB interval, including objects already collected. It diagnoses allocation churn, not exact allocations or live retained bytes. Module-cache lists and [GC performance entries](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html) are recorded only in diagnostics, so lazy dependency activation is observable. Inspector overhead makes diagnostic times ineligible for speed comparisons.

Memory mode forces GC at named checkpoints across three event-loop turns: harness, loaded provider, live fixture, first use, repeated work, closed-but-retained handles and released references. It records RSS, peak process RSS, heap total/used, external and ArrayBuffer bytes. ArrayBuffers overlap external accounting; RSS includes code, stacks, allocators and native memory. Rust payloads are not inferred from heapUsed. Post-GC plateaus are retention evidence, not proof that all finalizers ran. Compare window counts 1/8/32 and repeated create-close workloads in separate fresh processes. No forced collection is added to production code.

Parallel throughput includes messaging and scheduling in total work wall time, with pool startup and whole-process exit separately reported. Per-task work excludes task setup and close; total throughput includes both. All worker isolates have separate DOMs and dependency state. Process CPU and RSS cover all threads; never sum worker RSS. Use single-lane throughput as the control, and include pool startup for short-lived test jobs. Serial latency runs never overlap this experiment.

## Optimization decisions

Prioritize measured end-to-end savings over a fast isolated kernel. For every change record the source/cohort, dominant self/inclusive/allocation costs, expected upper bound from the cost share, semantic invalidation/lifetime risks, and before/after matched distributions. Re-run relevant owned/API/WPT/runner contracts before fresh serial measurements. Retain regressions and failed hypotheses.

Investigate shared immutable metadata and lazy initialization when first-window/first-CSS work dominates; reuse/caching when repeated reads dominate, with explicit live-state invalidation tests; raw-state algorithms when wrapper/reflection allocation dominates; Rust only when useful work amortizes validation/transfer/materialization; compression when measured transport cost exceeds encoding/decoding; worker parallelism for independent document batches. Capability parameterization must be explicit and tested: default drop-in behavior remains complete, and reduced capability experiments receive separate labels. Historical handoff speed claims cannot substitute for comparable recovered artifacts and workloads.

The matched `compare` report retains independent process distributions for provider loading, scenario setup and first use alongside warm-batch distributions. It archives its exact comparator and records host load/free memory before and after the matrix. The framework benchmark retains each trial's raw Vitest report, stdout/stderr, individual workflow durations and memory observation, with the producer-resolution guard enabled. Historical framework reports without these fields retain their narrower evidence scope.

`parse-html-unique` changes a checked source attribute on every operation; `parse-html-rotate` revisits four checked shells; `parse-html-traverse` verifies every row's text, attribute and document ownership. The original `parse-html` remains repeated-input construction. Unique worker tasks use disjoint operation ranges and negative warmup ranges, so parser caches remain cold for measured inputs while the worker/runtime can stay warm. Resetting task-local ordinals had allowed a supposed unique workload to reuse sixteen inputs; its reports remain archived and cannot support unique-input throughput claims. Whole-process wall time includes pool warmup and teardown as well as startup and measured task work.

`bun run benchmark:framework --include-turbo` adds TurboDOM 0.8.6 through its published `environment/vitest` export. The default command retains the original three providers. Every pool/provider is screened against the same eight workflows before timed trials; failure logs, exit status and trial directories stay in `failures`. Missing/partial rows carry sample counts and `eligible: false`, with null medians when no timing trials passed. Any failed screen makes the command exit nonzero after preserving the complete report. The TurboDOM adapter documents Vitest 1–4; running it against this repository's pinned Vitest 5 is an explicit integration check, not assumed compatibility.

The edge matrix must cover different cost families before selecting the next optimization. `list-reconcile` snapshots the full list, edits eight dispersed rows, replaces one row, and verifies IDs, owner documents, detachment and static-snapshot stability. An operation includes eight edits, one replacement and two snapshots. `interaction-state` activates a checkbox, requires exactly one change callback, updates a dispersed row in that callback, and checks computed style for both the selected row and the live `:checked` control. Dropped writes fail verification. Use small/large trees, deep event paths, repeated reads, mutation-heavy queries, multiple live windows and VM construction as separate controls; their differing operation counts cannot form one aggregate speed score.

## Explicit Node compile-cache configuration

Node's module compile cache is an opt-in runner configuration, measured separately from DOM algorithm changes. Set `NODE_COMPILE_CACHE` to a persistent writable directory when launching Node/Vitest; leave it unset for the default cohort. Node documents disk persistence and initial compilation overhead in its [module compile-cache API](https://nodejs.org/api/module.html#module-compile-cache). Record an empty-cache first invocation separately from later invocations with the same code and Node version. The DOM package does not change this process setting.

The frozen uVC4wn experiment accepts 324 rotated scenario trials: nine fresh processes for each provider/scenario/configuration, using disabled, empty and primed caches. Each of RunDOM, Happy DOM, TurboDOM and jsdom performs checked empty-window, role and unique-parse work. Process timing includes exit-time writes; 12 initial priming runs and cache bytes are retained. This includes benchmark harness compilation, so whole-process improvements are not attributed entirely to the DOM package. Evidence: `.cache/qualification/compile-cache-study-{status,summary}.json`.

A separate frozen installed Vitest fork experiment runs the same eight React workflows for RunDOM, Happy DOM and jsdom, accepting 81 trials. Disabled / empty / primed process medians are 683.60 / 840.74 / 625.88 ms for RunDOM, 690.20 / 894.51 / 640.98 for Happy DOM and 969.40 / 1313.97 / 820.77 for jsdom. Initial standalone priming costs are 942.69 / 943.09 / 1380.63 ms respectively. Test-body time is essentially unchanged for RunDOM; startup benefits require reuse and the initial cost must be amortized. All eight tests pass in every trial under the producer-resolution guard. This experiment covers forks, not every Vitest pool or coverage configuration. Evidence: `.cache/qualification/compile-cache-framework-{status,summary}.json`.

### Packed framework stress controls

`bun run benchmark:framework --include-stress --include-turbo` adds two real React/Vitest workloads to the existing eight-workflow fixture: 2,048 keyed rows reordered and updated through sixteen delegated clicks, and sixty-four checkbox/state/style transitions. Every iteration checks state; keyed rows retain node/control identity and an independently edited value. All providers receive byte-identical fixtures, and a failed screen remains ineligible. Ten-test stress reports carry a separate fixture hash and must not be compared directly to historical eight-test reports. Complete-process time, individual test durations and post-suite worker RSS remain separate. The packed four-pool conformance command always includes the stress contracts.

Completed processes must also satisfy the elapsed process budget, even when exit status is zero. System suspend/resume can delay a kill timer until after child exit; deadline callbacks alone cannot admit a timing trial. Failure records retain the measured duration. Timing summaries exclude budget-violating observations and mark the affected combination ineligible. A November 8 clamshell-sleep interruption invalidated the initial large-parse matrix; its raw report is preserved separately and is not accepted evidence. Idle-sleep assertions never override user-forced/clamshell sleep.

## Local real-project replay

`qualification/replay.sh` replays the `frameworks` (Vue, Svelte, MUI) and `extended` (Supabase UI, freeCodeCamp, React, Drone) jobs of `.github/workflows/qualify.yml` on a macOS or Linux workstation, with the same pinned revisions, test selections and provider wiring. It never runs from `bun run check`; each replay takes minutes and needs the network for setup. Checkouts and results live under `QUAL_DIR` (default `.cache/qualification-replay`). Rounds without explicit providers use the rotated orders candidate/reference/happy/turbo, turbo/happy/reference/candidate and reference/turbo/candidate/happy. Timing files use the CI `%e %M` format (wall seconds, peak RSS KiB) on both platforms; macOS needs coreutils `gtimeout`. The host must otherwise be idle, as for every timing run.

Assertion and pass/fail sets are exact. Durations, wall time, throughput and RSS come from shared CI hosts and only indicate where to look.

## Load-immune probe

Wall-clock time is unusable on a loaded host. `packages/jsdom/bench/lab/probe.ts` runs each fixed scenario in fresh `node --single-threaded` processes and reports numbers that host load barely moves: CommonJS and built-in modules loaded, which RunDOM artifacts loaded, interfaces and own keys installed on the Window, whether the CSS reference grammar was initialized, and whole-process instructions retired. On macOS instructions come from `/usr/bin/time -l`; on Linux from `perf stat -e instructions:u` when the host exposes the counter. Elsewhere the report degrades to in-process CPU time. Instructions cover the whole process, so subtract the `create` scenario (load plus one styled Window) to get a scenario's own share. Under a load average of 16–29, repeated runs within one invocation stayed within 1% in instructions, and separate invocations of two identical builds differed by up to 2%; probe before and after builds alternately and treat instruction differences under 3% as noise.

Scenarios: `create`, `globals-read` (every own Window property read once, as Vitest's `populateGlobal` does), `first-query`, `first-computed-style`, `visibility-reads` (2,000 ancestor-chain `display` plus `visibility` reads), `click` (2,000), `append-remove` (4,000), `domparser-repeat` (100 parses of a 256-row table) and `window-create-close` (100). Loop sizes are fixed so instruction counts compare across builds.

`packages/jsdom/bench/lab/probe-budget.json` holds generous inclusive `[min, max]` bounds on deterministic counts only; timing is never budgeted. The `probe` job in `qualify.yml` runs the probe with the budget, uploads `probe.json` as the `probe` artifact, and cannot fail the workflow. Tighten a bound when an optimization lowers a count; raise one only with the reason in the commit.

| `node packages/jsdom/bench/lab/probe.ts --entry /absolute/other/dist/jsdom.cjs --repeat 5`   | Probe another build, such as a frozen baseline, for a before/after table. |

| `node packages/jsdom/bench/lab/probe.ts --budget packages/jsdom/bench/lab/probe-budget.json` | Also list counts outside their bounds and exit 1 when any is breached.    |
